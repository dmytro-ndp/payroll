# Feature Specification: Імітаційний прототип системи нарахування заробітної плати

**Feature Branch**: `002-payroll-prototype`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "розроби імітаційний прототип об'єктно-орієнтованого проєкту, що реалізує інформаційну систему для предметної області \"Система нарахування заробітної плати підприємства\", мовою Java з мінімальною складністю: 1) без зовнішніх залежностей і без бази даних; 2) замість реальних операцій — повідомлення у консолі українською мовою; 3) проєкт компілюється і запускається з консолі; 4) в README.md в корні проєкту має бути опис прототипу і команди його компіляції і запуску з консолі. Реалізація має чітко дотримуватися документації прототипу в теці docs (usecase.puml, class.mmd, sequence.mmd, state.mmd, crc.xlsx) та принципів з конституції проєкту."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Видання наказу та формування відомості (Priority: P1)

Директор видає наказ, що дозволяє бухгалтеру проводити розрахунковий цикл; бухгалтер додає
працівників до відомості, доки наказ чинний.

**Why this priority**: Без чинного наказу жодна подальша дія (додавання працівника, нарахування)
неможлива — це базова передумова всього циклу й мінімальний демонстрований сценарій.

**Independent Test**: Запустити прототип з консолі, ініціювати видання наказу та додати одного
працівника до відомості — у консолі з'являються повідомлення українською про видання наказу й
успішне додавання працівника.

**Acceptance Scenarios**:

1. **Given** розрахунковий цикл щойно розпочато (стан «Очікування наказу»), **When** директор
   видає наказ, **Then** консоль повідомляє про видання чинного наказу й цикл переходить у стан
   «Формування відомості».
2. **Given** наказ чинний і відомість порожня, **When** бухгалтер додає нового працівника,
   **Then** консоль повідомляє про успішне додавання й цикл переходить (або лишається) у стані,
   що дозволяє нарахування.
3. **Given** наказ нечинний або відсутній, **When** бухгалтер намагається додати працівника,
   **Then** консоль повідомляє про відмову, а склад відомості не змінюється.
4. **Given** працівника вже додано до відомості, **When** бухгалтер повторно додає того самого
   працівника, **Then** консоль повідомляє про відмову через дублікат, а склад відомості не
   змінюється.

---

### User Story 2 - Нарахування заробітної плати (Priority: P2)

Бухгалтер ініціює нарахування заробітної плати для всіх працівників відомості за стандартним
правилом нарахування, за умови чинного наказу та непорожньої відомості.

**Why this priority**: Нарахування — головна цінність системи для предметної області; без нього
відомість не дає кінцевого результату, але воно можливе лише після успішного виконання P1.

**Independent Test**: Маючи відомість із щонайменше одним працівником і чинним наказом, запустити
нарахування — для кожного працівника з'являється консольне повідомлення про завершене
нарахування з сумою.

**Acceptance Scenarios**:

1. **Given** наказ чинний і відомість містить працівників, **When** бухгалтер ініціює
   нарахування, **Then** для кожного працівника консоль повідомляє про створене нарахування, і
   цикл переходить у стан «Нарахування завершено».
2. **Given** наказ нечинний, **When** бухгалтер ініціює нарахування, **Then** консоль повідомляє
   про відмову, і жодне нарахування не створюється.
3. **Given** відомість порожня, **When** бухгалтер ініціює нарахування, **Then** консоль
   повідомляє про відмову, і жодне нарахування не створюється.

---

### User Story 3 - Отримання квитанції працівником (Priority: P3)

Працівник, для якого нарахування вже завершене, запитує й отримує квитанцію з підсумком
нарахування.

**Why this priority**: Завершує цикл цінністю для кінцевого отримувача (працівника), але
залежить від результатів P1 і P2, тому має нижчий пріоритет демонстрації.

**Independent Test**: Після завершеного нарахування для працівника запросити квитанцію — консоль
виводить повідомлення із представленням квитанції цьому працівникові.

**Acceptance Scenarios**:

1. **Given** нарахування для працівника завершене, **When** працівник запитує квитанцію,
   **Then** консоль повідомляє про видачу квитанції з даними про працівника й суму нарахування.
2. **Given** нарахування для працівника ще не завершене (відсутнє), **When** працівник запитує
   квитанцію, **Then** консоль повідомляє про відмову без створення квитанції.

---

### Edge Cases

- Що відбувається, якщо наказ відкликають після того, як відомість уже сформовано: нарахування
  надалі неможливе, доки не з'явиться новий чинний наказ (`DirectorOrder`).
- Як система поводиться, коли той самий `Employee` (за ідентифікатором) намагаються додати
  повторно: відмова без зміни складу відомості.
- Що відбувається за спроби нарахування на порожній відомості: відмова без створення
  `PayrollCalculation`.
- Як система реагує на запит квитанції до завершення нарахування для конкретного працівника:
  відмова без створення `Receipt`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ПОВИННА дозволяти директору видати наказ (`DirectorOrder`), який є чинним
  одразу після створення, із виведенням відповідного повідомлення в консоль українською мовою.
- **FR-002**: Система ПОВИННА дозволяти перевіряти чинність наказу перед додаванням працівника до
  відомості та перед нарахуванням заробітної плати.
- **FR-003**: Система ПОВИННА дозволяти бухгалтеру додавати працівника (`Employee`) до відомості
  (`PayrollSheet`) лише за чинного наказу та лише якщо цього працівника ще немає у відомості;
  інакше операція ПОВИННА завершуватися відмовою без зміни складу.
- **FR-004**: Система ПОВИННА дозволяти бухгалтеру ініціювати нарахування заробітної плати для
  всіх працівників відомості лише за чинного наказу та непорожньої відомості; інакше операція
  ПОВИННА завершуватися відмовою без створення нарахувань.
- **FR-005**: Нарахування суми для кожного працівника ПОВИННО виконуватися через правило
  нарахування (`PayrollRule`), реалізоване конкретним класом `StandardPayrollRule`, що
  успадковує спільну абстрактну основу `BasePayrollRule`.
- **FR-006**: Результат нарахування для кожного працівника ПОВИНЕН зберігатися як окремий об'єкт
  `PayrollCalculation`, доступний для подальшого пошуку за працівником.
- **FR-007**: Система ПОВИННА дозволяти працівнику отримати квитанцію (`Receipt`) лише якщо для
  нього вже існує завершене нарахування; інакше запит ПОВИНЕН завершуватися відмовою без
  створення квитанції.
- **FR-008**: Видача квитанції ПОВИННА виводити в консоль повідомлення українською мовою з
  переліком отримувача й суми нарахування замість будь-якої реальної доставки чи друку.
- **FR-009**: Усі операції, що імітують зовнішню взаємодію (видання наказу, додавання працівника,
  нарахування, видача квитанції, відмови), ПОВИННІ виводити повідомлення в консоль виключно
  українською мовою; жодна реальна зовнішня операція (файл, мережа, база даних) не виконується.
- **FR-010**: Проєкт ПОВИНЕН компілюватися й запускатися виключно засобами командного рядка, без
  зовнішніх бібліотек, фреймворків чи систем керування базами даних.
- **FR-011**: Структура класів прототипу ПОВИННА відповідати `docs/class.mmd`: класи `Employee`,
  `DirectorOrder`, `PayrollSheet`, `PayrollCalculation`, `Receipt`, інтерфейс `PayrollRule`,
  абстрактний клас `BasePayrollRule` і клас `StandardPayrollRule`, із задокументованими
  зв'язками (композиція, агрегація, залежність, успадкування, реалізація).
- **FR-012**: Послідовність взаємодій під час виконання сценаріїв ПОВИННА відповідати
  `docs/sequence.mmd`, включно з гілками відмови, що не змінюють стан.
- **FR-013**: Переходи між станами розрахункового циклу ПОВИННІ відповідати `docs/state.mmd`
  («Очікування наказу» → «Формування відомості» → «Готовність до нарахування» → «Нарахування» →
  «Нарахування завершено» → «Видача квитанції» → завершення циклу), включно з переходами
  відмови, що повертають цикл у той самий стан.
- **FR-014**: Відповідальності кожного класу ПОВИННІ відповідати єдиній відповідальності,
  задокументованій у відповідній CRC-картці `docs/crc.xlsx`.
- **FR-015**: Залежності між об'єктами (наприклад, `PayrollSheet` і `PayrollRule`) ПОВИННІ
  передаватися через конструктор або setter-метод; статичні методи для впровадження залежностей
  НЕ ПОВИННІ використовуватися.
- **FR-016**: Назви класів, методів і атрибутів ПОВИННІ бути англійською мовою; коментарі в коді
  та всі консольні повідомлення ПОВИННІ бути українською мовою.
- **FR-017**: У корені проєкту ПОВИНЕН бути файл `README.md`, що описує призначення прототипу та
  містить точні команди для його компіляції й запуску з консолі.
- **FR-018**: Запуск прототипу з консолі ПОВИНЕН демонструвати щонайменше один повний
  розрахунковий цикл: видання наказу, додавання одного чи кількох працівників, нарахування та
  отримання квитанції принаймні одним працівником.

### Key Entities *(include if feature involves data)*

- **Employee**: Працівник підприємства, якого включають до відомості; ідентифікується унікальним
  `employeeId` та має повне ім'я.
- **DirectorOrder**: Наказ директора, що є передумовою додавання працівників і нарахування; має
  стан чинності, який можна скасувати (відкликати).
- **PayrollSheet**: Відомість нарахування, що керує складом унікальних працівників, посилається
  на чинний наказ і утримує список завершених нарахувань.
- **PayrollCalculation**: Результат нарахування заробітної плати для одного працівника — сума,
  обчислена правилом нарахування.
- **Receipt**: Квитанція, що подає працівникові підсумок завершеного нарахування.
- **PayrollRule / BasePayrollRule / StandardPayrollRule**: Контракт, спільна основа та конкретна
  реалізація правила обчислення суми нарахування для працівника.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Користувач може скомпілювати та запустити прототип єдиною послідовністю команд
  командного рядка без установлення додаткового програмного забезпечення.
- **SC-002**: Повний демонстраційний цикл (наказ → додавання працівника → нарахування → видача
  квитанції) відтворюється одним запуском програми й виводить в консоль послідовні повідомлення
  українською мовою для кожного кроку.
- **SC-003**: 100% спроб додати працівника або розпочати нарахування без чинного наказу
  завершуються повідомленням про відмову без зміни складу відомості чи появи нарахувань.
- **SC-004**: 100% спроб повторно додати того самого працівника до відомості завершуються
  повідомленням про відмову без зміни її складу.
- **SC-005**: 100% спроб отримати квитанцію до завершення нарахування для відповідного
  працівника завершуються повідомленням про відмову без створення квитанції.
- **SC-006**: Усі повідомлення, що з'являються під час виконання програми, написані українською
  мовою й не містять технічних стек-трейсів чи повідомлень іншою мовою за штатного сценарію.

## Assumptions

- Сума нарахування, яку обчислює `StandardPayrollRule`, є демонстраційним фіксованим або умовним
  значенням (наприклад, базовою ставкою), оскільки реальні тарифні дані виходять за межі
  прототипу й не зберігаються в жодному зовнішньому джерелі.
- Один запуск програми демонструє один розрахунковий цикл для невеликої заданої в коді кількості
  працівників; введення даних інтерактивно з консолі не є обов'язковим для мінімальної
  складності прототипу.
- Прототип виконується в межах одного процесу без паралельних користувачів; питання
  багатопотокового доступу до стану не входять до обсягу цієї специфікації.
- Назва предметної області для конституції (`TODO(SUBJECT_DOMAIN)`) відповідає «Система
  нарахування заробітної плати підприємства», задокументованій у цьому прототипі.
