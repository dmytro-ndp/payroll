# Завдання: Імітаційний прототип системи нарахування заробітної плати

**Вхідні дані**: Проєктні документи з `/specs/002-payroll-prototype/`

**Передумови**: `plan.md` (обов'язково), `spec.md` (обов'язково для user stories), `research.md`,
`data-model.md`, `contracts/console-cli.md`, `quickstart.md`

**Тести**: Явного запиту на TDD/формальний тестовий набір у специфікації немає. Автоматизована
самоперевірка реалізується як окремий клас `SelfCheck` без зовнішніх фреймворків (рішення
`research.md` §6) і винесена в завершальну фазу (Polish), оскільки перевіряє сценарії всіх трьох
user stories одночасно.

**Організація**: Завдання згруповано за user stories зі `spec.md`, щоб кожну історію можна було
реалізувати та перевірити окремо (на рівні прямих викликів доменних класів, без повного запуску
`Main`, як описано в розділах «Independent Test» специфікації).

## Формат: `[ID] [P?] [Story] Опис`

- **[P]**: Можна виконувати паралельно (різні файли, без залежностей від незавершених завдань)
- **[Story]**: До якої user story належить завдання (US1, US2, US3)
- У кожному завданні вказано точний шлях до файлу

## Угода про шляхи

Один консольний Java-проєкт (single project) без build-інструментів:

- Вихідний код: `src/ua/payroll/`, `src/ua/payroll/model/`, `src/ua/payroll/rule/`
- Скомпільовані класи: `bin/` (не версіюється)
- Документація прототипу: `README.md` у корені репозиторію

чинний; дублікати відхиляються без зміни складу (FR-001–FR-003, FR-019, FR-020).

повідомлення про видання наказу, успішне додавання кожного унікального працівника та відмову через

## Залежності та порядок виконання

### Залежності фаз

- **Налаштування (Phase 1)**: без залежностей — можна починати одразу
- **Фундаментальні завдання (Phase 2)**: залежать від завершення Phase 1; блокують усі user
  stories
- **User Stories (Phase 3–5)**: усі залежать від завершення Phase 2; через єдиний файл `Main.java`
  і клас `PayrollSheet`, що розширюються в кожній наступній історії, стadії виконуються
  послідовно за пріоритетом P1 → P2 → P3 (а не повністю паралельно різними виконавцями)
- **Завершальна фаза (Phase 6)**: залежить від завершення всіх трьох user stories

### Залежності між user stories

- **User Story 1 (P1)**: починається після Phase 2; не залежить від інших historій
- **User Story 2 (P2)**: починається після Phase 2; розширює `PayrollSheet` і `Main.java`,
  створені в US1 (T007, T009, T010), але логіка `calculate` залишається окремо перевірюваною
  викликом методу напряму
- **User Story 3 (P3)**: починається після Phase 2; розширює `PayrollSheet` і `Main.java`,
  створені в US1/US2 (T007, T014), але `findCalculation`/`Receipt` перевіряються незалежно за
  готовим `PayrollCalculation`

### У межах кожної user story

- Моделі/правила створюються перед методами, що їх використовують
- Зміни `PayrollSheet` передують відповідному кроку в `Main.java`
- Історія вважається завершеною перед переходом до наступної за пріоритетом

### Можливості для паралельного виконання

- T002 (Setup) можна виконувати паралельно з T001
- T004, T005, T006 (Phase 2) — різні файли, можна виконувати паралельно після T003
- T011 (US2) можна починати одразу; T012 залежить від T011, а T013 — від T012
- T019, T020 (Phase 6) — різні файли, можна виконувати паралельно

## Стратегія реалізації

### Спочатку MVP (лише User Story 1)

1. Завершити Phase 1: Налаштування
2. Завершити Phase 2: Фундаментальні завдання (КРИТИЧНО — блокує всі historії)
3. Завершити Phase 3: User Story 1
4. **ЗУПИНИТИСЯ й ПЕРЕВІРИТИ**: самостійно протестувати видання наказу й формування відомості
5. Продемонструвати за потреби вже на цьому етапі

### Інкрементна доставка

1. Завершити Налаштування + Фундаментальні завдання → основа готова
2. Додати User Story 1 → перевірити незалежно → MVP готовий до демонстрації
3. Додати User Story 2 → перевірити незалежно → демонстрація нарахування
4. Додати User Story 3 → перевірити незалежно → демонстрація повного циклу з квитанцією
5. Завершальна фаза: `SelfCheck`, `README.md`, інтегрований сценарій, ручна перевірка,
   перевірка конституції

## Примітки

- `[P]` — різні файли, без залежностей між собою
- Мітка `[Story]` прив'язує завдання до конкретної user story для трасованості
- Через єдиний інтерактивний сценар `Main.java` і спільний клас `PayrollSheet` user stories цього
  прототипу виконуються послідовно (P1 → P2 → P3), а не повністю незалежними командами, однак
  кожна зберігає власний незалежний спосіб перевірки на рівні прямих викликів методів
- Фіксувати зміни (коміт) після кожного завдання або логічної групи завдань
- Зупинятися на кожній контрольній точці для незалежної перевірки історії
- Уникати: розпливчастих завдань, конфліктів в одному файлі без зазначеної послідовності,
  міжісторійних залежностей, що порушують незалежну перевірюваність
