# Контракт консольного інтерфейсу (CLI)

**Функціональність**: `specs/002-payroll-prototype/spec.md`

Прототип не має програмного API — єдиний інтерфейс, яким користуються актори (директор,
бухгалтер, працівник, представлені тут одним користувачем консолі), це послідовність
текстового вводу/виводу через stdin/stdout під час одного запуску `Main`. Цей документ визначає
контракт цієї взаємодії: обов'язкові запити, формат відповідей і повідомлення, що мають
з'явитися для кожного результату.

## Загальні правила контракту

- Увесь вивід програми — українською мовою (FR-009, FR-016).
- Кожен крок сценарію: програма виводить запит (prompt) → користувач вводить рядок → програма
  виводить результат (успіх або відмова) одним або кількома рядками `System.out`.
- Відмова ніколи не завершує процес аварійно (без необроблених винятків/стек-трейсів, SC-006);
  вона виводить пояснювальне повідомлення й дозволяє продовжити сценарій.

## Крок 0 — Перевірка нарахування без чинного наказу

- **Вхід**: відповідь «так» на пропозицію виконати демонстраційну перевірку.
- **Дія**: програма створює тестовий наказ, відкликає його, встановлює правило через
  `PayrollSheet.setPayrollRule(...)` і запускає `calculate()`.
- **Вихід**: повідомлення про відмову без створення нарахувань (FR-004, FR-020, SC-003).
- Відмова не завершує процес; після неї починається основний розрахунковий цикл.

## Крок 1 — Видання наказу

- **Вхід**: ідентифікатор наказу (рядок, зчитується один раз на початку).
- **Вихід (успіх)**: повідомлення про видання чинного наказу з його ідентифікатором.
- Відповідає FR-001; відкликання наказу (`revoke()`) у базовому сценарії не викликається
  користувачем напряму в основному циклі; його використовує лише контрольована перевірка Кроку 0.

## Крок 2 — Формування відомості (цикл додавання працівників)

- **Вхід**: кількість працівників для спроби додавання (ціле число) і далі для кожної спроби —
  ідентифікатор та повне ім'я працівника.
- **Вихід (успіх)**: повідомлення про успішне додавання працівника до відомості.
- **Вихід (відмова — дублікат)**: повідомлення про відмову через повторний `employeeId`
  (FR-003, FR-020); склад відомості не змінюється.
- **Вихід (відмова — нечинний наказ)**: повідомлення про відмову через відсутність чинного
  наказу (FR-002, FR-003); склад відомості не змінюється.
- Приклад сценарію з Q2/Q4: користувач навмисно вводить `employeeId`, який уже використав раніше
  в цьому ж запуску, щоб побачити повідомлення про відмову-дублікат.

## Крок 3 — Передчасний запит квитанції

- **Вхід**: ідентифікатор доданого працівника до початку нарахування.
- **Вихід**: повідомлення про відмову без створення квитанції (FR-007, FR-020, SC-005).
- Після відмови відомість та її працівники залишаються без змін.

## Крок 4 — Нарахування заробітної плати

- **Вхід**: команда/підтвердження початку нарахування (наприклад, порожній ввід Enter або
  коротка команда).
- **Вихід (успіх)**: для кожного працівника відомості — повідомлення про створене нарахування з
  іменем працівника та сумою (FR-005, FR-006).
- **Вихід (відмова — нечинний наказ або порожня відомість)**: повідомлення про відмову без
  створення нарахувань (FR-004).

## Крок 5 — Отримання квитанції

- **Вхід**: ідентифікатор працівника, для якого запитується квитанція.
- **Вихід (успіх)**: повідомлення про видачу квитанції з іменем працівника й нарахованою сумою
  (FR-007, FR-008).
- **Вихід (відмова — нарахування відсутнє)**: повідомлення про відмову без створення квитанції
  (FR-007, FR-020); доступно для демонстрації, якщо користувач запитує квитанцію для працівника
  без завершеного нарахування (наприклад, доданого, але до виконання Кроку 3).

## Завершення

- Після видачі принаймні однієї квитанції (або за командою завершення) програма виводить
  підсумкове повідомлення й завершує роботу з кодом виходу `0`.
