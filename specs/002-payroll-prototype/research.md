# Дослідження: Імітаційний прототип системи нарахування заробітної плати

**Функціональність**: `specs/002-payroll-prototype/spec.md`
**Дата**: 2026-10-16

Усі пункти Технічного контексту в `plan.md` визначені однозначно на основі специфікації,
конституції (`.specify/memory/constitution.md`) та наявної документації в `docs/`; маркерів
`NEEDS CLARIFICATION` немає. Цей документ фіксує обґрунтування ключових технічних рішень, що
впливають на подальше проєктування (Phase 1) і декомпозицію завдань.

## 1. Версія Java та спосіб збирання

- **Decision**: Java 17 (LTS), компіляція й запуск лише командами `javac`/`java` без Maven/
  Gradle чи інших build-інструментів.
- **Rationale**: Конституція (принцип IV) вимагає локальне виконання з командного рядка без
  зовнішніх сервісів; FR-010 прямо забороняє зовнішні бібліотеки та фреймворки. JDK 17 —
  поширена LTS-версія з синтаксисом, достатнім для простих POJO-класів без додаткових
  можливостей, що ускладнили б навчальний приклад.
- **Alternatives considered**: Maven/Gradle-проєкт — відхилено, бо вносить build-інструмент як
  зовнішню залежність всупереч принципу мінімальної складності (I) та FR-010; новіші версії
  Java (21+) — відхилено, бо не додають потрібних можливостей і зменшують сумісність середовищ
  навчального курсу.

## 2. Консольний ввід даних

- **Decision**: `java.util.Scanner` над `System.in` у класі `Main` для отримання кількості
  працівників, повного імені кожного та команд переходу між кроками сценарію (уточнення Q1).
- **Rationale**: Стандартна бібліотека, без додаткових залежностей; `Scanner` — найпростіший
  спосіб читання рядків/чисел із консолі в Java SE.
- **Alternatives considered**: `BufferedReader` + `System.in` — функціонально рівноцінний, але
  вимагає ручного парсингу чисел; `java.io.Console` — непридатний у середовищах без інтерактивного
  терміналу (наприклад, деякі IDE/CI), тоді як `Scanner` над `System.in` працює з перенаправленим
  вводом, що також спрощує відтворюваний ручний прогон за `quickstart.md`.

## 3. Підхід до демонстрації відмов у єдиному запуску

- **Decision**: `Main` не форсує відмови автоматично; сценарій лише дає користувачеві змогу
  своїм вводом (повторити ім'я, запросити нарахування до наказу чи квитанцію до завершення
  нарахування) викликати кожну з трьох відмов (уточнення Q2/Q4). `README.md` і `quickstart.md`
  наводять приклад послідовності вводу, що гарантовано демонструє всі відмови за один прогін.
- **Rationale**: Відповідає рішенню користувача (Q4) і зберігає `Main` простим координатором
  без прихованої автоматичної логіки, що ускладнила б читання сценарію.
- **Alternatives considered**: Автоматична примусова демонстрація відмов незалежно від вводу —
  відхилено користувачем на користь контрольованого сценарію введення.

## 4. Обчислення суми нарахування

- **Decision**: `StandardPayrollRule.calculate(Employee)` повертає фіксовану константу
  (`BigDecimal`), однакову для всіх працівників, оголошену в класі правила (уточнення Q3).
- **Rationale**: `Employee` (за `docs/class.mmd`) не містить атрибута ставки/окладу; введення
  такого атрибута розширило б модель поза межами затвердженої діаграми класів. Фіксована
  константа — найпростіший спосіб задовольнити FR-005 без зміни `docs/class.mmd`.
- **Alternatives considered**: Ввід ставки користувачем для кожного працівника — відхилено
  користувачем (Q3, варіант A обрано замість B); обчислення за похідними даними `Employee`
  (наприклад, довжина `employeeId`) — відхилено як штучне й менш прозоре для демонстрації.

## 5. Представлення грошової суми

- **Decision**: `java.math.BigDecimal` для суми нарахування (атрибут `amount` у
  `PayrollCalculation`, позначений як `decimal` на `docs/class.mmd`).
- **Rationale**: `BigDecimal` — стандартний у Java SE тип для грошових сум без похибок
  двійкової арифметики з рухомою крапкою; відповідає типу `decimal` у `class.mmd` без
  додавання зовнішніх бібліотек.
- **Alternatives considered**: `double`/`float` — відхилено через ризик похибок округлення,
  неприйнятний навіть для демонстраційних грошових сум.

## 6. Стратегія перевірки (тестування) без зовнішніх залежностей

- **Decision**: Самостійний клас `SelfCheck` (або еквівалентний допоміжний клас) у вихідному
  коді, що викликає публічний API доменних класів для сценаріїв успіху й відмови та звіряє
  результат власними перевірками (`if`/`throw` або `assert`), виводячи підсумок у консоль
  українською; `README.md`/`quickstart.md` також документують ручний прогін через `Main`.
- **Rationale**: FR-010 і принцип I забороняють зовнішні бібліотеки, тож JUnit чи інші
  тест-фреймворки виключені. Простий клас з `main`-методом перевірки — мінімально складний
  спосіб автоматизованої перевірки, сумісний із компіляцією лише `javac`.
- **Alternatives considered**: JUnit — відхилено як зовнішню залежність; відсутність будь-якої
  автоматизованої перевірки — відхилено, бо ускладнює підтвердження SC-003–SC-005 без ручного
  повторення кожного разу.

## 7. Обробка станів розрахункового циклу

- **Decision**: Стан цикла (`WaitingForOrder` → `FormingSheet` → `ReadyToCalculate` →
  `Calculating` → `CalculationCompleted` → `IssuingReceipt`) не моделюється окремим class/enum,
  а випливає неявно з комбінації полів `DirectorOrder.isActive()` і складу/вмісту
  `PayrollSheet` (чи порожня відомість, чи є нарахування) — перевірки в методах `PayrollSheet`
  відтворюють переходи й відмови з `docs/state.mmd` без надлишкового окремого класу стану.
- **Rationale**: Принцип мінімальної складності (I): явний клас стану (`State`/енум з
  переходами) додав би рівень абстракції, не обов'язковий для демонстрації шести станів і
  чотирьох операцій одного циклу.
- **Alternatives considered**: Явний `enum PayrollCycleState` з перевіркою переходів —
  відхилено як надмірний для обсягу прототипу; залишено можливість додати в майбутньому, якщо
  кількість станів чи правил переходів зросте.
